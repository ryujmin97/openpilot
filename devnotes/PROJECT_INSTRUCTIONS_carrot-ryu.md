# CARROT-MS 프로젝트 진행 지침 (v2)
(ryujmin97/openpilot 기반 · Claude 세션 연속 진행용)

이 문서는 매 세션 시작 시 Claude가 가장 먼저 확인해야 하는 프로젝트 기준 문서다.
**이 문서 자체가 Source of Truth다.** `carrot-ryu-note` 브랜치의
`devnotes/PROJECT_INSTRUCTIONS_carrot-ryu.md`에 보관되며, 매 세션 첫 도구 호출로
조회한다(4절). 계정/기기가 바뀌어도 이 파일 하나만 최신으로 유지하면 모든 세션이
동일한 기준을 따른다.

> **v2 안내**: v1(1~27차)은 회차마다 규칙을 덧붙이고 지난 이력을 모두 문서 안에
> 남기는 방식이라 문서가 계속 길어지고, 확정된 규칙과 "그때 있었던 사고 설명"이
> 뒤섞여 있었다. v2부터는 현재 유효한 규칙만 담고, 상세 변경 사유는 이 파일의
> GitHub 커밋 메시지로 대체한다.
> **절 번호는 v1과 동일하게 유지한다** (0~19, 최종 목표 요약). WIP.md/FINDINGS.md/
> CURRENT_STATUS.md 등 기존 devnotes에 이미 "9절", "16절", "18절" 같은 절 번호
> 인용이 다수 있고, 그중 WIP.md/FINDINGS.md는 수정 금지(불변) 원칙이 적용되는
> 파일이라 절 번호를 재배치하면 과거 기록의 인용이 전부 틀어진다. 그래서 v2는
> 병합·재배치 없이 "같은 번호, 같은 주제, 다듬어진 문장"만 적용했다. 앞으로
> 새 절을 추가해야 하면 기존 번호 사이에 끼워 넣지 말고 항상 뒤(19절 다음)에
> 이어 붙인다.

- Claude 환경에 bash_tool(코드 실행)이 있으면, GitHub 조회(`raw.githubusercontent.com`,
  `api.github.com`, `git ls-remote`)에 `curl`/`git`을 직접 사용하는 것을 우선한다.
  `web_fetch` 계열 도구는 브랜치명 URL에서 CDN 캐시로 인해 push 직후 예전 내용을
  반환하는 경우가 실제로 있었으나(45차-정정 세션에서 실증), bash_tool의 `curl`은 이
  문제 없이 항상 최신을 반환했다. bash_tool이 없는 세션에서는 4절 0단계의 SHA 고정
  방식을 그대로 따른다.

## 2. carrot-ms 동기화(Sync) 원칙
────────────────────────────────
carrot-ms는 매번 재생성(rebase)되어 hash가 바뀌므로 커밋 메시지/내용 기준으로
추적한다.

1. `WIP_SYNC.md`에서 마지막으로 검토·반영 완료로 기록된 커밋 목록 확인
2. GitHub API/git으로 happymaj11r/openpilot(carrot-ms) 체크포인트 이후 신규 커밋
   전체를 대상으로 한다 -- carrot-wip(ajouatom/openpilot)에도 있는지 여부로 미리
   걸러내지 않는다(과거 "carrot-wip에 없고 carrot-ms에만 있는 커밋만 추린다" 필터는
   폐지, 115차. carrot-wip에 이미 있는 커밋도 carrot-ms를 통해 새로 노출된 이상 내
   차량 관련성은 별개로 판단해야 함이 실증됨 -- 상세는 WIP_SYNC.md 115차 참고)
3. 그중 WIP_SYNC.md에 이미 검토된 것 제외 → 미검토 커밋만 내 차량에 필요한지 판단
4. 필요하면 사용자에게 어떤 커밋을 어떻게 반영할지 제안 → 승인 후 9절 방식으로 반영
5. 반영 결과(가져온 커밋/제외한 커밋과 이유/충돌 여부)를 WIP_SYNC.md에 기록
6. 후보가 많으면 한 세션에 몰아 반영하지 않고 여러 세션에 나눈다
7. 모델셀렉터 관련 여부(클러스터 HUD, PC 시뮬레이터 등 커밋 종류)로 미리 제외하지
   않는다(과거 "모델셀렉터와 무관한 커밋은 기본 제외" 규칙은 폐지, 115차). 신규
   커밋은 전부 개별 분석해 내 차량(제네시스 DH 2015 + 콤마 C3) 관련성을 판단하고,
   관련 없다고 판단한 커밋은 제외 사유를 WIP_SYNC.md에 기록한다. 반영 여부는
   4번대로 사용자 승인 후에만 결정
- carrot-ms/carrot-wip 원본은 절대 직접 수정하지 않는다. 조회해서 carrot-ryu로
  가져오는 방향으로만 사용한다.

## 4. 새 세션 시작 시 확인 순서 (지연 로딩, 무료 사용량 절약)
────────────────────────────────
전체 파일을 다 읽지 않는다. 필요한 만큼만, 아래 순서로 확인한다.

**0단계 — 이 지침 문서 조회 (세션의 첫 도구 호출, 필수)**
raw.githubusercontent.com의 브랜치명 URL은 CDN 캐시로 인해 최근 push 이후에도
한동안 예전 내용을 반환할 수 있다. 이를 원천 차단하기 위해 항상 다음 순서로
조회한다:
  1. `git ls-remote https://github.com/ryujmin97/openpilot.git carrot-ryu-note` 로
     그 브랜치의 현재 HEAD 커밋 SHA를 먼저 얻는다. (API rate limit에 걸리면
     `api.github.com/repos/ryujmin97/openpilot/commits?sha=carrot-ryu-note&per_page=1`
     로 대체)
  2. 그 SHA로 고정한 raw URL
     (`https://raw.githubusercontent.com/ryujmin97/openpilot/<SHA>/devnotes/PROJECT_INSTRUCTIONS_carrot-ryu.md`)
     로 이 문서를 조회한다. 커밋 SHA는 콘텐츠 주소 방식이라 캐시 stale이
     구조적으로 발생할 수 없다.
  3. 같은 세션에서 HANDOFF.md 등 carrot-ryu-note의 다른 파일을 조회할 때도
     1번에서 얻은 SHA를 재사용한다(브랜치당 ls-remote 1회면 충분).
  4. 조회를 마치면 세션의 첫 응답 안에서 "지침 문서 확인함(버전: v2, 커밋
     `<SHA 앞 7자리>`)" 형태로 사용자에게 짧게 보고한다. 이 언급이 없다면 0단계를
     건너뛴 것이므로, 사용자는 즉시 작업을 중단시키고 0단계부터 다시 시키면 된다.

**이후 필요한 것만 조회**
1. `devnotes/HANDOFF.md` — 직전 세션 인수인계 (거의 항상 필요)
2. `devnotes/CURRENT_STATUS.md` — 현재 상태 요약
3. carrot-ryu 최신 commit (GitHub API)
4. `devnotes/WIP.md` — 이전 작업 이어갈 때만 (최상단 회차 위주)
5. `devnotes/LAST_ANALYZED.md` — 분석 범위 정할 때만
6. `devnotes/FINDINGS.md` — 원인 분석/이슈 기록할 때만
7. `devnotes/PARAMS_REGISTRY.md` — 튜닝 파라미터 다룰 때만
8. `devnotes/WIP_SYNC.md` — carrot-ms 동기화 이력 확인할 때만
9. `devnotes/toolkit/README.md` — 로그 분석 스크립트 작업할 때만
10. happymaj11r(carrot-ms)/ajouatom(carrot-wip) — 비교·동기화 필요할 때만

이 조회들은 Claude가 읽기 전용으로 직접 수행하며 사용자 스크립트 실행이 필요 없다
(9절 스크립트는 "쓰기/반영" 전용).

## 5. 작업 흐름 (기본 사이클)
────────────────────────────────
1. Claude가 carrot-ryu용 코드 변경사항 작성
2. devnotes 기록 작성(carrot-ryu-note용, 코드와 별도)
3. 사용자에게 두 묶음 전달: (a) carrot-ryu 반영 스크립트, (b) carrot-ryu-note 반영
   스크립트 — 각각 실행 방법 포함, 두 브랜치를 한 스크립트에 섞지 않음
4. 사용자가 PowerShell에서 그대로 실행 → 임시 clone → 반영 → commit/push → 임시
   폴더 자동 삭제
5. 다음 세션이 두 브랜치의 GitHub 최신 상태부터 이어받음

- 사용자가 실제로 스크립트를 실행해 push하기 전까지는 "반영된 것"으로 간주하지
  않는다. 실행 로그가 중간에 끊겼거나 스크립트가 끝까지 갔는지 불확실하면, 로그만
  보고 완료로 단정하지 않고 GitHub API/raw 조회로 직접 재확인한다(16절).
- 세션이 한도에 가까워지면 미완성이라도 현재까지 상황을 devnotes에 기록하고
  안전하게 마무리한다(17절).

## 6. Base Commit 원칙
────────────────────────────────
- 작업 시작 시 carrot-ryu/carrot-ryu-note 각각의 현재 commit을 확인한다.
- 반영 스크립트는 실행 시점에 항상 새로 clone하므로 자동으로 최신 위에서 동작하지만,
  Claude가 스크립트를 "작성"하는 시점과 사용자가 "실행"하는 시점 사이에 시차가
  있으므로, 특히 코드 파일처럼 내용이 얽힌 변경은 스크립트 작성 직전에 해당 파일의
  GitHub 최신 버전을 다시 조회한 뒤 그 위에서 구성한다(9절 문자열 블록 치환에서
  특히 중요 — anchor가 최신 원본과 정확히 일치해야 유일 매치가 성립).
- carrot-ms는 hash가 계속 바뀌므로 특정 hash로 base를 고정하지 않고, WIP_SYNC.md의
  검토 완료 커밋 메시지 목록을 기준으로 삼는다.
- 충돌 여부가 불확실하면 임의로 진행하지 않고 사용자에게 보고한다. `git push`가
  non-fast-forward 등으로 실패하면 사용자는 에러를 그대로 Claude에게 전달하고,
  임의로 `--force`를 쓰지 않는다.

## 7. WIP.md 작성 규칙 (carrot-ryu-note 브랜치)
────────────────────────────────
- 회차는 마크다운 헤더로 구분: `## N차 (상태 요약) — 제목`
- 새 회차는 파일 최상단에 추가한다(최신이 위).
- 기존 회차는 삭제·수정·순서변경하지 않는다.
- 같은 회차를 이어갈 때는 "## N차 계속", "## N차 계속2" 형식.
- 오래된 내용을 임의로 축약/삭제하지 않는다. 필요하면 사용자에게 먼저 제안한다.
- 이 "최상단 추가만" 규칙 덕분에, 반영 스크립트는 파일 전체를 다시 보낼 필요 없이
  새 회차 텍스트만 담아 기존 파일 맨 위에 이어붙이면 된다(9절).

────────────────────────────────
## 8. HANDOFF.md 작성 규칙 (carrot-ryu-note 브랜치)
────────────────────────────────
가능하면 다음 항목을 포함한다: Worker / Date / Repository / Code Branch(base
commit) / Note Branch(base commit) / carrot-ms 마지막 검토·동기화 커밋(메시지
기준) / 작업 / 완료 / 미완료 / 검증 / 주의사항 / 다음 작업.

이 파일은 "항상 최신 1개 버전만 유지"하는 성격이라, 반영 시 전체 내용을 새로
구성해 통째로 교체한다(9절의 "교체형" 파일).

────────────────────────────────
## 9. 작업 결과물 전달 규칙 (매번 필수)
────────────────────────────────
기본 방식: PowerShell(PC, 기본) / Termux(폰, 사용자가 명시할 때만) 스크립트를
파일로 생성해 전달 + 실행 명령은 채팅에 별도 안내. 스크립트 전체를 채팅에
그대로 붙여넣지 않는다(토큰 낭비).

**스크립트 구조**
1. `$RepoUrl`, `$Branch`, `$CommitMsg` 등 변수 설정
2. 임시 폴더에 해당 브랜치를 `git clone --branch <branch> --single-branch --config core.autocrlf=false`
   (CRLF/LF 불일치로 인한 블록 매칭 실패 방지)
3. 파일 반영 — 유형별 처리:
   - 이어붙이기형(누적 파일): `WIP.md`, `WIP_SYNC.md`, `FINDINGS.md`,
     `PARAMS_REGISTRY.md` 등은 새로 추가할 내용만 담아 기존 파일 최상단(제목 줄
     바로 아래)에 삽입. 파일 전체를 옮기지 않는다.
   - 교체형(요약 파일): `CURRENT_STATUS.md`, `HANDOFF.md`,
     `PROJECT_INSTRUCTIONS_carrot-ryu.md`(19절 승인 시) 등은 전체 내용을 담아
     통째로 덮어쓴다.
   - 코드 파일 — 소규모 변경: 문자열 찾아바꾸기(`-replace`, 라인 치환).
   - 코드 파일 — 신규/전면 재작성: 전체 내용을 담아 교체.
   - 코드 파일 — 부분 수정(기본 방식): 변경 전/후 블록을 통째로 here-string으로
     담아, "변경 전 블록"이 파일 전체에서 정확히 1회만 존재하는지 확인한 뒤
     `.Replace()`로 교체(Replace-Block 패턴). CRLF/LF 불일치에 대비해 매칭 전
     정규화 비교도 병행한다. 1회가 아니면(0회/2회 이상) 그 자리에서 중단하고
     아무것도 건드리지 않은 채 사용자에게 보고 — 강제 진행 금지(15절과 동일 원칙).
   - diff/patch(`git apply`): 문자열 블록 치환으로 처리하기 어려운 예외적
     경우(파일 안에 멀리 떨어진 수십 곳의 짧은 변경이 흩어진 경우)에만 보조
     수단으로 사용. 반드시 `git apply --check`로 먼저 검증하고, 실패 시 즉시
     중단(강제 적용/무시 금지, 15절과 동일 원칙).
   - 소스(js/css) 수정 시 필수: 소스만 고치고 끝내지 않는다. 그 자리에서
     `npm install && node build.mjs`로 생성 번들(`js/generated/`, `css/generated/`,
     `generated/asset-manifest.json`)을 재생성하고, 그 diff까지 커밋에 포함한다.
     기기는 소스가 아니라 커밋된 번들을 그대로 서빙하므로, 소스만 맞고 번들이
     어긋나면 diff는 정상으로 보여도 실기기에는 효과가 없다. 번들 안에 문제의
     식별자가 축약되지 않고 원문 그대로 남아있으면 번들링 실패 신호다.
4. `git add` → `git commit -m $CommitMsg` → `git push origin $Branch`
5. `git push` 성공(로그로 확인)이 확인되기 전에는 로컬 다운로드 폴더의 `.ps1`
   파일을 삭제하라고 권하지 않는다(재시도 대비). 임시 clone 폴더는 스크립트가
   스스로 정리(`Remove-Item -Recurse -Force`).

**PowerShell 필수 규칙**
- 파일 읽기/쓰기(`Get-Content`, `Set-Content`, `[System.IO.File]::...`)는 항상
  `Join-Path $Tmp "상대경로"` 형태의 절대경로 사용. `Set-Location`으로 위치를
  옮겨도 일부 .NET API는 프로세스 시작 디렉터리 기준으로 상대경로를 해석해
  실패할 수 있다(`DirectoryNotFoundException`). `git` 명령 자체는 이 문제가
  없으니, 가능하면 `git -C <경로>`로 셸의 현재 위치 자체를 바꾸지 않는 편을 권장.
- 대상 파일(devnotes/코드) 전체를 재작성할 때는 `Set-Content -Encoding UTF8`을 쓰지 않는다.
  Windows PowerShell 5.1의 `Set-Content`/`Out-File -Encoding UTF8`은 원본에 BOM이 없어도
  항상 새로 UTF-8 BOM(`EF BB BF`)을 붙이는데(PowerShell 7의 `UTF8NoBOM`과 달리 5.1에는 그런
  옵션이 없음), 대상 파일은 BOM 없는 편이 `git diff`/`grep`/Python 파서와 호환에 유리하다
  (84차 계속2, 핵심 발견 41에서 4개 파일 전체가 이 방식으로 인해 오염된 채 push된 사례 발생).
  전체 재작성에는 `[System.IO.File]::WriteAllText($Path, $Content, (New-Object
  System.Text.UTF8Encoding($false)))`만 사용하고, 쓴 직후 대상 파일 첫 3바이트를 확인해
  BOM이 없음을 검증한다(아래 "전달 전 필수 자가검증 체크리스트" 참고).
- devnotes(`WIP.md`/`CURRENT_STATUS.md`/`HANDOFF.md` 등) 편집에 Python 스크립트를 사용할
  때는 파일을 열 때 `open(path, ..., newline="")`을 지정해 원본 개행 문자(LF/CRLF)를
  그대로 보존한다. Python 텍스트 모드 쓰기(`newline=None`, 기본값)는 Windows에서 `\n`을
  `\r\n`으로 자동 변환하는데, 이는 git의 `core.autocrlf=false`(git clone 단계 설정)로는
  막을 수 없는 별개의 변환이라, 원본과 다른 개행 스타일로 파일 전체가 바뀌거나 같은
  브랜치 안 파일끼리 개행 스타일이 서로 달라질 수 있다(56차에서 실증: Python으로 쓴
  `WIP.md`/`CURRENT_STATUS.md`는 CRLF로, `.NET WriteAllText`로 쓴 `HANDOFF.md`는 LF로
  남아 서로 불일치했음).
- 전달하는 `.ps1` 파일 자체에 한글 등 비ASCII 문자가 있으면 반드시 UTF-8 BOM을
  포함해 생성한다. Windows PowerShell 5.1은 BOM 없는 `.ps1`을 시스템 코드페이지
  (CP949 등)로 잘못 해석해, 대상 파일 인코딩 지정과 무관하게 스크립트 안 한글
  문자열 자체가 이미 깨진 채로 커밋될 수 있다.
- 실행 명령은 항상 다음 2줄 형태로 안내(기본 실행 정책이 `.ps1`을
  `UnauthorizedAccess`로 막는 것과, 우회 시 뜨는 확인 프롬프트를 함께 방지):
  ```
  Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
  & "$HOME\Downloads\script_name.ps1"
  ```

**전달 전 필수 자가검증 체크리스트 (핵심 발견 17·21(26/39차)·37·41·42 재발 방지)**
`.ps1` 파일을 생성한 뒤, 사용자에게 전달(present_files)하기 전에 아래를 전부 실행하고 그 결과
(명령 출력)를 응답에 포함한다. 서술("BOM 포함했습니다", "체크리스트를 지켰습니다")만으로는
충분하지 않고, 검증 명령의 실제 출력을 보여준다. 다른 세션이 만든 반영 스크립트를 이어받아 실행하는
경우에도 동일하게 적용한다(핵심 발견 26/39차).
1. 비ASCII 문자가 포함된 `.ps1`이면 첫 3바이트가 `EF BB BF`인지 확인(`od -An -tx1 -N3 <path>` 등).
2. 스크립트 안의 모든 `git clone`에 `--config core.autocrlf=false`가 포함돼 있는지 확인.
3. `finally` 블록에 임시 폴더 `Remove-Item -Recurse -Force`가 있는지, 사용자에게 수동 삭제를
   요청하는 문구가 없는지 확인.
4. `py_compile` 등 정적 검증을 포함하는 스크립트는 `python3`/`python` 단순 호출 대신, `py -3` ->
   `python3` -> `python` 순으로 실제 `--version` 출력을 확인하는 `Get-PythonCmd` 패턴을 기본값으로
   사용한다(필요할 때만 추가하는 것이 아니라 항상 기본값). Python을 외부 프로세스로 호출하는 모든
   지점(버전 확인 + 실제 검증 실행 모두)은 표준입력에 빈 문자열을 미리 파이프해 EOF를 공급한다
   (`"" | & $Cmd @Args 2>&1`) -- 특정 환경에서 인자 전달 문제로 인터랙티브 REPL에 빠져 스크립트가
   무한 대기하는 사고(핵심 발견 43, 84차 계속2)를 구조적으로 차단하기 위함이며, 이 경우에도 종료
   코드와 실제 출력을 응답에 남겨 "그냥 통과"로 오판하지 않는다.
5. 대상 파일(devnotes/코드)을 전체 재작성하는 모든 쓰기는 `[System.IO.File]::WriteAllText(...,
   UTF8Encoding($false))`만 사용하고, 쓴 뒤 대상 파일 첫 3바이트가 BOM이 아닌지 확인한다(핵심
   발견 41).
6. 이어붙이기형 파일(WIP.md 등)에 anchor 치환을 적용했다면, 매치 횟수(1회)뿐 아니라 치환 *결과*
   텍스트(특히 파일 맨 앞/헤더 줄)를 다시 읽어 의도한 내용과 같은지 확인한다(핵심 발견 42 --
   "1회 매치"는 "그 자리에서 치환이 일어났다"만 보증하지 "결과가 의도와 같다"는 보증하지 않는다).
7. 앵커/치환 문자열(`$Old`/`$New`)이 있는 스크립트는, 전달 전에 *전달할 .ps1 파일에서* 그 문자열을
   그대로 추출해 대상 파일의 SHA 고정 원본에 시뮬레이션한다(매치 정확히 1회 + 치환 결과 텍스트
   확인). 앵커는 기억이 아니라 최신 SHA 원본에서 복사하고, 새로 추가한 검증 코드도 같은 방식으로
   시뮬레이션하며, 그 출력을 응답에 포함한다(핵심 발견 45).
8. `.ps1`을 전달하기 전에 `pwsh`(PowerShell 7)의 파서로 구문 오류가 0건인지 확인한다:
   `[System.Management.Automation.Language.Parser]::ParseFile($Path,[ref]$tokens,[ref]$errs)` 후
   `$errs.Count`와 오류 메시지(줄/열)를 출력한다. PowerShell은 파일 전체를 실행 전에 파싱하므로 배열
   리터럴의 후행 쉼표(`@(..., )`)처럼 한 곳만 틀려도 스크립트가 시작 즉시 죽는다(123차 devnotes v1
   4057행). 같은 파서가 후행 쉼표 합성 파일을 오류로 잡는지 대조군도 한 번 확인한다. 샌드박스에 pwsh가
   없으면 GitHub 릴리스 tarball(`https://github.com/PowerShell/PowerShell/releases/download/vX.Y.Z/powershell-X.Y.Z-linux-x64.tar.gz`)을
   직접 받아 설치한다(`api.github.com`은 rate limit으로 실패할 수 있음). PowerShell 7 파서 기준이며
   Windows PowerShell 5.1 실행을 대신하지 않는다.
9. 반영 스크립트(코드/devnotes)는 전달 전에 로컬 bare 저장소를 대상으로 끝까지 실행해 본다. 대상
   브랜치의 SHA 고정 트리로 만든 bare 저장소를 `$RepoUrl`로 쓰고(시뮬레이션용 사본은 저장소 URL과
   Linux용 경로 구분자만 바꾸고 로직은 그대로 둔다), 두 모드로 실행한다: (a) 일반 체크아웃, (b) Windows
   CRLF 체크아웃 재현(`GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.eol GIT_CONFIG_VALUE_0=crlf`). 각
   모드에서 push된 커밋의 `git show --numstat`(변경량이 의도와 같은지), 파일별 blob hash(스크립트의
   `Post` 값과 일치), 이어붙이기형 파일은 기존 줄 삭제 없이 삽입만 있는지를 출력으로 확인한다(CRLF
   체크아웃 때문에 앵커 매치가 실패해 안전 중단된 사례: 121차 v1, 핵심 발견 48). 이 검증도 Windows
   PowerShell 5.1 실제 실행이 아니라는 한계를 결과 보고에 명시한다.

**공통 원칙**
- 코드는 carrot-ryu, devnotes는 carrot-ryu-note — 한 스크립트에 두 브랜치를
  섞지 않는다. 둘 다 필요하면 스크립트를 나눈다.
- 인증은 사용자 장치에 이미 설정된 git 인증 수단(Credential Manager, gh CLI 로그인
  등)으로 push 시점에 처리된다. Claude는 어떤 인증정보도 요구·전달받지 않는다
  (15절).
- 보조 방식(GitHub 웹 UI 수동 반영)은 파일이 매우 크거나 바이너리이거나
  사용자가 스크립트 실행이 어려운 상황일 때만 사용. 이 경우도 반영 브랜치를 매번
  명시적으로 안내.
- 매번 함께 전달: (1) 스크립트 파일 + 실행 명령, (2) 반영 브랜치/파일 목록,
  (3) 보조 방식 사용 시 파일 경로·웹 UI 절차·권장 커밋 메시지.
- 스크립트 실행 로그(특히 `git commit`/`git push` 출력)를 사용자가 전달하면 그걸로
  정상 반영 여부를 판단하되, 로그가 끊겼거나 불확실하면 GitHub API/raw 조회로
  직접 재확인한다(16절). "완료" 로그가 찍혔어도, 코드 파일처럼 중요한 반영은
  raw.githubusercontent.com(SHA고정)으로 실제 내용을 재조회해 확인하는 걸 권장.
- 같은 세션 안에서 동일 대상(코드 또는 devnotes)에 대해 스크립트를 다시 작성해야
  하면, 파일명에 버전 표시(`-v2`, `-final` 등)를 붙여 사용자 PC Downloads 폴더의
  이전 로컬 파일과 이름이 겹치지 않게 한다. 이름이 겹치면 사용자가 실수로 구버전
  로컬 파일을 실행할 위험이 있다(45차-정정 세션에서 실제 발생: 중간 초안과 최종본이
  같은 파일명으로 두 번 전달되어, devnotes에는 중간 초안이 반영되고 코드에만 최종본이
  반영되는 불일치가 생겼음).

## 10. 코드 수정 원칙
────────────────────────────────
- 최소 변경 원칙: 필요한 파일/코드만 수정, 관련 없는 리팩터링/파라미터 변경 금지.
- carrot-ms 대비 무엇이 왜 달라졌는지 항상 설명 가능하게 유지(향후 충돌 최소화).
- 코드는 항상 carrot-ryu 기준으로만 작업하며, carrot-ryu-note에는 코드 파일을
  두지 않는다.
- 새 `Params.get()`/`.put()` 키를 코드에 추가할 때는 같은 반영 스크립트/커밋 안에서
  `openpilot/common/params_keys.h`에도 함께 등록한다. 등록이 빠지면 코드는 정상으로
  보여도 실행 시 `UnknownKeyName` 예외로 조용히 실패한다(핵심 발견 12, FINDINGS.md
  2026-09-14/22차 사례).

## 11. 분석 원칙
────────────────────────────────
- 추측만으로 원인을 확정하지 않는다: 증상 → 재현조건 → 입력 → 상태 → 호출흐름 →
  계산 → 조건/분기 → 출력 → 원인 → 수정안 → 검증.
- 커밋 분석도 필요한 범위부터 단계적으로 확장: 커밋 목록 → diff → 변경 파일 →
  변경 함수 → 호출자 → 호출되는 함수. openpilot 전체를 불필요하게 다 훑지 않는다.

────────────────────────────────
## 12. 실차 검증 표기 원칙
────────────────────────────────
- 정적 분석/시뮬레이션만 했다면 "실차 검증"했다고 표현하지 않는다. 실제로 하지
  않은 검증을 했다고 보고하지 않는다. 예: 실차 검증: 미실시 로 명확히 표기.
- carrot-ryu의 최종 검증 경로는 항상 콤마 디바이스 + 제네시스 DH 2015 실주행이다.

## 15. GitHub 커밋/인증 관련
────────────────────────────────
- 실제 커밋/push는 항상 사용자가 직접 수행(웹 UI 클릭 또는 스크립트 실행).
- Claude는 PAT/비밀번호/SSH 키 등 어떤 인증정보도 요구·전달받지·보관하지 않는다.
- 강제 덮어쓰기(`git push --force` 등 히스토리를 지우는 행위)는 하지 않는다.
  편집/교체/이어붙이기는 일반적인 새 커밋이라 문제없지만, 삭제 후 재생성 같은
  큰 구조 변경은 사전에 사용자에게 알린다.
- push가 non-fast-forward로 거부되면 임의로 `--force`를 쓰지 않고 상황을 먼저
  공유한다.
- diff/patch가 `git apply`에 실패하거나 문자열 블록 치환이 정확히 1회로 매치되지
  않았는데 무시하고 강제로 다음 단계(commit/push)를 진행하는 것도 이 원칙 위반
  이다 — 반드시 중단하고 보고한다.

## 16. GitHub 상태가 예상과 다를 경우
────────────────────────────────
임의로 진행하지 않고 먼저 GitHub 실제 상태를 재확인 → 판단이 안 서면 사용자에게
보고. 해당하는 경우:
- devnotes 내용과 실제 코드 상태가 다름 / base commit이 존재하지 않음
- 같은 파일에 예상 못한 변경이 있음 / 반영 여부가 불명확함
- carrot-ryu와 carrot-ryu-note 사이에 코드·devnotes가 섞여 있음
- carrot-ms에 새 커밋(모델셀렉터 관련)이 있는데 WIP_SYNC.md에 검토 기록이 없이
  오래 방치됨
- ryujmin97/openpilot에 carrot-ms/carrot-wip이 다시 나타나는 등 브랜치 구성이
  문서와 다름
- devnotes에 기록된 마지막 회차와 실제 GitHub 최신 상태 사이에 괴리가 있음(예:
  문서에는 "완료"로 서술됐으나 devnotes 자체에는 해당 회차 기록이 없는 경우 —
  실제로 그 세션이 있었는지, 기록만 누락된 것인지 확인)
- 사용자가 반영 스크립트를 실행했다고 알렸는데 로그에 에러가 있었거나, 로그를
  아직 확인 못한 경우 — 완료로 가정하지 않고 GitHub API로 재확인
- 실행 로그가 스크립트 끝(`commit`/`push`/완료 메시지)까지 도달하지 못하고 끊긴
  경우 — 화면에 안 보이는 것인지 실제로 멈춘 것인지 구분 안 되므로 반드시
  GitHub에서 직접 재확인
- "완료"로 끝났어도 코드 파일처럼 중요한 반영은 raw 조회(SHA고정)로 실제 내용을
  재확인
- 세션 첫 응답에 "지침 문서 확인함(버전/커밋)" 언급이 없는 경우 — 4절 0단계가
  누락됐을 가능성이 높으므로, 사용자는 스크립트 실행 전에 0단계부터 다시
  수행하도록 요청

## 20. 브랜치 버전 관리 (carrot-ryu-vN 아카이브 + 재생성)
────────────────────────────────
- 배경: 2절의 개별 커밋 선별 반영 방식은 carrot-ms에 신규 커밋이 쌓일수록(특히 종방향/
  Hyundai CAN/eGPU처럼 carrot-ryu가 독자적으로 병행 발전시켜 온 영역) 세션마다 위험도
  판단 부담이 누적된다. 이를 완화하기 위해, 격차가 커졌다고 사용자가 판단하는 시점에
  아래 절차로 carrot-ryu를 carrot-ms 최신 베이스 위에서 한 번에 재구성할 수 있다.
- carrot-ryu는 콤마 디바이스가 실제로 추적/배포하는 브랜치이므로 이름을 절대 바꾸지
  않는다. 버전 전환은 "아카이브 생성 → carrot-ryu 재생성" 순서로, carrot-ryu라는 이름
  자체는 항상 유지한 채 그 내용(HEAD가 가리키는 커밋)만 바뀐다.

**절차**
1. 사용자가 리셋 시점을 지정한다(2절의 신규 커밋 누적 상황을 참고하되, 고정된 기준
   개수를 두지 않고 매번 사용자가 판단).
2. 현재 carrot-ryu HEAD를 그대로 가리키는 새 브랜치 `carrot-ryu-vN`(N은 1부터 순차
   증가)을 생성해 스냅샷으로 보관한다. 기존 커밋을 그대로 복제해 새 참조를 만드는
   것뿐이라 히스토리 파괴가 없다(15절의 강제 push 금지와 무관, force 불필요).
3. carrot-ryu-vN은 생성 이후 절대 수정하지 않는다(과거 기록 전용, WIP.md/FINDINGS.md와
   동일한 불변 원칙). 새 작업은 항상 carrot-ryu에서만 진행한다.
4. carrot-ms 현재 HEAD를 새 베이스로 삼아 carrot-ryu를 재생성한다. 이는 기존 carrot-ryu
   히스토리를 통째로 교체하는 작업(강제 push와 동등한 효과)이므로, 15절의 "삭제 후
   재생성" 예외 사례로 취급한다 — 매번 실행 직전에 사용자에게 명확히 알리고 명시적
   승인을 받은 뒤에만 진행하며, 임의로 선행하지 않는다.
5. carrot-ryu-vN의 "코드 수정 현황"(CURRENT_STATUS.md의 번호 리스트)을 이식 체크리스트로
   삼아, 항목별로 새 베이스 위에 하나씩 재적용한다. 이식은 git cherry-pick을 기본
   수단으로 삼지 않는다(베이스 구조 자체가 크게 바뀐 영역은 conflict 위험이 크므로).
   9절의 기존 워크플로(Replace-Block/전체교체 + py_compile·테스트 검증)를 그대로
   따른다.
6. 이식은 한 세션에 몰아서 끝내지 않고 17절 원칙대로 영역/항목 단위로 나눠 진행한다.
   진행 상황(완료/보류/제외 항목과 사유)은 WIP_SYNC.md에 "버전 리셋 이력"으로 기록한다.
7. 이식과 정적 검증이 모두 끝났더라도, 재생성된 carrot-ryu를 실제로 디바이스에
   배포(git pull 유도)하기 전에는 사용자에게 다시 한번 확인받는다 — 재생성 직전
   상태(=carrot-ryu-vN)가 이미 디바이스에 설치돼 실주행 중일 수 있기 때문이다.
8. carrot-ryu-vN 아카이브는 조회도 원칙적으로 하지 않는다(필요할 때만 예외적으로
   참고). carrot-ms/carrot-wip처럼 외부 미러링 대상이 아니라 우리 자신의 과거
   스냅샷이므로 1절의 "존재해야 하는 브랜치" 원칙에 대한 명시적 예외로 취급한다.
- 2절(개별 커밋 선별 반영)과 이 20절(버전 리셋)은 병행 가능한 서로 다른 도구다.
  어느 시점에 어느 쪽을 쓸지는 매번 사용자가 정하며, 이 문서가 둘 중 하나를
  자동으로 우선하지 않는다.

## 21. 다중 AI(Claude·ChatGPT) 공동작업 원칙
────────────────────────────────
- 배경: 이 프로젝트는 세션 단위로 Claude와 ChatGPT가 번갈아 작업할 수 있다. 한 AI가
  세션을 마치면 다른 AI가 이어받거나, 다시 원래 AI가 이어받을 수 있다.
- 이 문서(0~20절 및 이 21절)는 Claude 전용이 아니라, 이 프로젝트에 참여하는 모든 AI가
  공통으로 따르는 기준 문서다. 어떤 AI든 새 세션을 시작할 때는 4절의 확인 절차(이
  문서 → HANDOFF.md → CURRENT_STATUS.md → 필요시 나머지)를 그대로 따른다. 3절의
  원칙(GitHub의 현재 상태 > AI의 기억 > 채팅에 붙여넣어진 과거 사본)도 AI 종류와
  무관하게 동일하게 적용된다.
- HANDOFF.md의 `Worker` 항목에는 이번 세션을 수행한 AI 이름(Claude 또는 ChatGPT,
  필요하면 모델명까지)을 명시한다. 다음 세션을 시작하는 AI는 직전 Worker가 자신과
  다른 AI였더라도 HANDOFF.md/CURRENT_STATUS.md/WIP.md의 최신 내용을 기준으로 동일하게
  이어받는다 — AI가 바뀌었다는 이유로 별도 취급하거나 처음부터 다시 분석하지 않는다.
- WIP.md의 회차 번호(N차)는 AI 종류와 무관하게 하나의 연속된 시퀀스로 유지한다.
  Claude가 진행한 회차와 ChatGPT가 진행한 회차를 구분해 별도로 번호 매기지 않는다.
  다만 어떤 AI가 그 회차를 수행했는지는 회차 헤더나 본문에 명시한다(예: `## N차
  (ChatGPT) — 제목`, 이미 `## N차 (상태 요약) — 제목` 형식을 쓰는 7절 규칙과 자연스럽게
  결합).
- 각 AI가 실제로 쓰는 조회 도구(터미널 bash_tool, 브라우저, 다른 코드 실행 환경 등)는
  서로 다를 수 있다. 도구가 달라도 결과 원칙은 동일해야 한다: 항상 GitHub의 최신
  상태(가능하면 커밋 SHA 고정)를 조회하고, 캐시되었거나 오래된 사본(채팅 기록, 이전
  세션 요약 등)을 최신으로 간주하지 않는다. bash_tool/curl처럼 0단계에서 권장하는
  수단이 없는 환경이면 웹 UI 조회, GitHub API, 또는 사용자에게 파일 내용 확인을
  요청하는 등 대체 수단을 쓰되, 어떤 수단으로 확인했는지 세션 응답에 남긴다.
- 실제 반영(commit/push)은 이전과 동일하게 항상 사용자가 스크립트를 실행하거나 웹
  UI에서 직접 수행한다(9절, 15절). 이 원칙은 어떤 AI가 작업했는지와 무관하게 그대로
  적용된다 — 어떤 AI도 GitHub 인증정보(토큰/비밀번호/SSH 키)를 요구·전달받지·보관하지
  않는다.
- 같은 시점에 두 AI가 같은 브랜치에 동시에 작업하지 않는다. 세션은 항상 순차적으로
  진행되며, 다음 AI는 이전 세션이 push까지 끝난 이후의 GitHub 최신 상태에서
  시작한다(6절의 Base Commit 원칙과 동일하게 적용).
- 두 AI 사이에 설명 방식, 스크립트 문법(예: PowerShell/bash 선택), 문장 스타일 등이
  다를 수 있으나, 이 문서에 정의된 브랜치 역할(1절)·파일 종류별 반영 방식(9절)·코드
  수정 원칙(10절)·전달 형식·금지 사항(18절)은 AI 종류와 무관하게 동일하게 적용한다.
  특정 AI만을 위한 예외 규칙은 만들지 않는다.
- 19절의 "이 지침 자체의 변경" 절차(변경 이유 → 기존 규칙 → 변경안 → 사용자 승인 →
  변경 → GitHub 저장)는 어떤 AI가 제안하든 동일하게 적용된다.
